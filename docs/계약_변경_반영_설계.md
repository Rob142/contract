# 청구 후 계약 변경 반영 설계

> 작성 2026-11-13 · 대상: 백엔드·DB·프론트 · 상태: **구현 완료** (11장 참고)

## 1. 문제

선금을 이미 청구했거나 받은 뒤에 수정 계약서가 오는 경우를 지금은 처리할 수 없다.

- 청구 기록(`billing_allocations`)은 계약 버전의 지급 단계(`payment_terms`)에 묶여 있다.
- 프로젝트를 새 계약으로 바꾸면 "이미 청구한 단계"라는 정보가 사라진다. 그러면 받은 선금을 또 청구할 수 있게 된다.
- 그래서 지금은 청구가 하나라도 있으면(초안·취소 포함) 교체와 해제를 막아 두었다 (`contract_has_billing`).

**목표:** 청구·입금 기록은 그대로 두고, 프로젝트를 새 계약 조건으로 옮긴다. 이미 청구한 금액은 새 계약의 단계로 **이월**해서 중복 청구를 막는다.

## 2. 예시

| | v1 (원계약) | v2 (수정 계약) |
|---|---|---|
| 계약 금액 | 1,000,000원 | 1,200,000원 |
| 지급 단계 | 선금 500,000 (**청구·입금 완료**) · 잔금 500,000 (청구 전) | 선금 500,000 · 중도금 300,000 · 잔금 400,000 |

반영 결과:

| v2 단계 | 단계 금액 | 이전 계약에서 이월 | 앞으로 청구 가능 |
|---|---|---|---|
| 선금 | 500,000 | 500,000 (v1 선금) | 0 |
| 중도금 | 300,000 | 0 | 300,000 |
| 잔금 | 400,000 | 0 | 400,000 |

- v1 선금 인보이스와 입금확인서는 그대로 남는다. 발행본은 원래 바꿀 수 없다.
- v1 잔금은 청구한 적이 없으므로 옮길 것이 없다. 그냥 사라진다.

## 3. 핵심 결정

### 3.1 기록은 고치지 않고 "이어 붙인다"

이미 발행한 인보이스의 배분(`billing_allocations.payment_term_id`)을 새 단계로 바꿔 끼우지 않는다. 발행본 불변 원칙과 감사 추적을 지키기 위해서다.

대신 **"이 옛 단계는 이 새 단계로 이어진다"**는 연결(승계)을 따로 기록한다. 새 단계의 청구액은 다음 둘을 더한 값이다.

```
새 단계의 청구액 = 새 단계에 직접 배분된 금액
                + 이 단계로 이어진 옛 단계들에 배분된 금액 (취소 제외, v1→v2→v3처럼 여러 번 이어져도 모두)
```

나중에 옛 인보이스를 취소하면 이월액도 자동으로 줄어든다. 따로 저장한 숫자가 아니라 매번 계산하기 때문이다.

### 3.2 무엇을 이어 붙여야 하나

- **취소되지 않은 청구가 있는 옛 단계만** 반드시 새 단계 하나에 연결한다.
- 청구가 없는 옛 단계는 연결하지 않는다.
- 여러 옛 단계를 새 단계 하나로 모을 수 있다 (N:1). 옛 단계 하나를 여러 새 단계로 쪼개지는 않는다. 쪼개려면 배분 금액을 나눠야 하고, 그건 기록을 고치는 일이 되기 때문이다.
- 새 단계에 이월되는 금액은 그 단계 금액을 넘을 수 없다.

### 3.3 범위: 같은 계약의 새 버전만

- 청구 후 변경은 **같은 계약서의 새 버전(v2, v3…)**으로만 허용한다. 청구 이력은 하나의 계약 계보에 속하게 한다.
- 지금은 업로드할 때마다 새 계약(v1)이 생긴다. "수정 계약서 올리기"는 기존 계약에 버전을 추가하는 별도 경로로 만든다.
- 다른 계약서로 통째로 바꾸는 기존 "교체"는 지금처럼 **청구 전에만** 된다. 잘못 연결한 경우를 위한 기능이다.

## 4. 데이터 모델 (마이그레이션 0004)

### 4.1 새 표: `payment_term_successions`

```sql
CREATE TABLE payment_term_successions (
  id                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id             uuid NOT NULL,
  project_id           uuid NOT NULL,
  predecessor_term_id  uuid NOT NULL REFERENCES payment_terms (id) ON DELETE RESTRICT,
  successor_term_id    uuid NOT NULL REFERENCES payment_terms (id) ON DELETE RESTRICT,
  created_by           uuid NOT NULL,
  created_at           timestamptz NOT NULL DEFAULT now(),
  UNIQUE (predecessor_term_id),               -- 옛 단계는 한 곳으로만 이어진다
  CHECK (predecessor_term_id <> successor_term_id),
  FOREIGN KEY (project_id, owner_id) REFERENCES projects (id, owner_id) ON DELETE CASCADE
);
CREATE INDEX ON payment_term_successions (successor_term_id);
```

- 행은 추가만 하고 고치지 않는다. 다시 바꾸면(v3) v2 단계 → v3 단계 행이 새로 붙는다.
- 한 번 쓴 계약 버전은 다시 고르지 않으므로 순환은 생기지 않는다. 서버가 "현재 버전보다 새 버전만" 받는 것으로 보장한다.

### 4.2 함수: 단계의 실제 청구액

```sql
-- statuses: 'issued' 만, 또는 'issued','draft' (후보 계산용)
CREATE FUNCTION term_billed_total(p_term uuid, p_statuses text[]) RETURNS numeric AS $$
  WITH RECURSIVE lineage(term_id) AS (
    SELECT p_term
    UNION
    SELECT s.predecessor_term_id FROM payment_term_successions s JOIN lineage l ON s.successor_term_id = l.term_id
  )
  SELECT COALESCE(sum(ba.amount), 0)
    FROM billing_allocations ba
    JOIN invoice_items ii ON ii.id = ba.invoice_item_id
    JOIN invoices i ON i.id = ii.invoice_id
   WHERE ba.payment_term_id IN (SELECT term_id FROM lineage)
     AND i.status = ANY(p_statuses)
$$ LANGUAGE sql STABLE;
```

### 4.3 바꿀 트리거와 규칙

| 대상 | 지금 | 변경 |
|---|---|---|
| 발행 시 과다 청구 검사 (`02_billing_rules.sql`) | 그 단계에 직접 배분된 발행액만 합산 | `term_billed_total(term, '{issued}')`로 계보 전체 합산 |
| **새 불변식** 배분 대상 검사 | 없음 | 초안·발행 배분은 **프로젝트 현재 계약 버전의 단계**에만 둘 수 있다. 이미 발행된 옛 배분은 그대로 유효하다 |
| `payment_term_successions` | — | 수정·삭제 금지 트리거 (추가만) |

### 4.4 계산을 바꿀 곳

- `services/projects.py` `term_billing()` → 이월액(`carried_amount`)과 그 출처 인보이스를 함께 돌려준다.
- `services/invoices.py` 청구 후보(`allocated_by_term`) → 계보 합산.
- **재발행** (`services/invoices.py` 389행 부근): 취소본의 배분이 옛 단계를 가리키면, 승계 표를 따라 **현재 단계로 바꿔서** 새 초안을 만든다. 현재 단계에 남은 한도가 부족하면 막고 안내한다.
- 대시보드 "청구할 단계" 할 일 → 계보 합산 기준.

## 5. API

### 5.1 수정 계약서 올리기

`POST /contracts/{contract_id}/versions` (multipart, 기존 업로드와 같은 검사) → 202 + 작업.

- `version_no = 최신 + 1`. 추출 → 조건 확인 흐름은 기존과 같다.
- 조건 확인 화면에 **이전 버전 확인값을 나란히** 보여 준다 (금액·납기·지급 조건 변경 표시).
- 계약서 목록·상세의 `project_id`는 **최신 버전이 아니라 계약의 어느 버전이든** 연결된 프로젝트를 돌려주도록 고친다. 지금처럼 최신 버전만 보면 v2가 "프로젝트 없음"으로 보인다.

### 5.2 반영 초안

`POST /projects/{project_id}/revision-draft` `{ "contract_version_id": "…" }` → 저장하지 않는 초안.

```json
{
  "from_version": { "id": "…", "version_no": 1, "contract_amount": "1000000" },
  "to_version":   { "id": "…", "version_no": 2, "contract_amount": "1200000" },
  "old_terms": [
    { "term_id": "…", "label": "선금 50%", "amount": "500000",
      "billed": "500000", "paid": "500000", "draft": "0",
      "invoices": [{ "id": "…", "invoice_no": "INV-2026-0001", "status": "issued" }],
      "must_carry": true },
    { "term_id": "…", "label": "잔금 50%", "amount": "500000", "billed": "0", "must_carry": false }
  ],
  "new_terms": [ { "key": "t1", "stage": "deposit", "label": "선금", "amount": "500000", "requirement": "…" }, … ],
  "proposed_carry": [ { "from_term_id": "…", "to_key": "t1" } ],
  "due_date": "2026-12-20"
}
```

자동 제안 규칙: 같은 `stage`이고 순서가 같은 단계를 먼저 고른다. 그다음 같은 `stage`, 마지막으로 남은 한도가 가장 큰 단계를 고른다.

### 5.3 반영

`POST /projects/{project_id}/revise-contract` (Idempotency-Key 필수, 프로젝트 `version` 낙관적 잠금)

```json
{
  "contract_version_id": "…",
  "version": "<project.version>",
  "contract_amount": "1200000",
  "due_date": "2026-12-20",
  "payment_terms": [ { "key": "t1", "stage": "deposit", "label": "선금", "amount": "500000", "requirement": "…", "due_date": null }, … ],
  "carry": [ { "from_term_id": "…", "to_key": "t1" } ]
}
```

서버가 한 트랜잭션에서 하는 일:

1. 프로젝트, 현재 단계들, 대상 버전을 잠근다 (`FOR UPDATE`).
2. 검사한다.
   - 대상 버전이 **같은 계약**이고, 현재 버전보다 **새 버전**이며, 조건 확인을 마쳤고(`ready`·`analyzed`), 다른 프로젝트에 쓰이지 않는다.
   - 단계 합계가 계약 금액과 같다.
   - 취소되지 않은 청구가 있는 옛 단계는 **모두 정확히 한 번** `carry`에 있다. 청구가 없는 단계는 `carry`에 올 수 없다.
   - 새 단계마다 이월 합계(발행 + 초안)가 단계 금액 이하이다.
3. 새 단계를 만들고, 승계 행을 추가하고, 프로젝트의 `contract_version_id`·`contract_amount`·`due_date`를 바꾼다.
4. 옛 단계를 가리키는 **초안** 배분을 대응하는 새 단계로 옮긴다. 초안은 원래 고칠 수 있는 문서다.
5. 감사 기록 `project.revise_contract` (이전·이후 버전, 이월 내역)을 남긴다.

오류 코드: `revision_not_newer`, `revision_other_contract`, `carry_missing`, `carry_not_needed`, `carry_exceeds_term`, `amount_below_billed`, `terms_total_mismatch`, `version_conflict`.

## 6. 화면

### 6.1 들어가는 곳

- 프로젝트 → 지급 단계 카드 → **"수정 계약서 반영"**. 청구 후에도 열린다. 기존 "계약서 교체"는 청구 전 전용으로 그대로 둔다.
- 계약서 상세 → **"수정 계약서 올리기"** (새 버전 업로드).
- 대시보드 "지금 할 일": 연결된 계약에 반영하지 않은 확인 완료 새 버전이 있으면 **"수정 계약 반영하기"**를 띄운다.

### 6.2 순서

1. 수정 계약서 올리기 (v2) → 추출
2. 조건 확인. 이전 값과 비교해서 보여 준다: `계약 금액 1,000,000 → 1,200,000`
3. **반영 확인 화면** (07 변형)
   - 위: 바뀌는 점 요약 (금액·납기·단계 수)
   - 왼쪽 "이미 청구한 단계": 단계마다 청구·입금 상태와 인보이스 링크, **"이어 붙일 새 단계"** 선택
   - 오른쪽 "새 지급 단계": 고칠 수 있다. 단계마다 `단계 금액 / 이월 / 앞으로 청구 가능`을 보여 준다
   - 청구 전 옛 단계: "청구한 적이 없어 새 단계로 대체돼요"
   - 초안: "초안 인보이스 n건은 새 단계로 옮겨져요"
   - 확인란 → "수정 계약 반영"
4. 프로젝트로 돌아온다. 지급 단계 옆에 `이전 계약에서 이월 500,000원` 표시와 출처 인보이스 링크가 보인다.

### 6.3 기록 보기

- 계약서 상세에 버전 목록(v1 이전 · v2 현재)을 두고, 이전 버전 원문을 읽기 전용으로 연다.
- 프로젝트 활동 기록에 "11/13 계약 v1 → v2 반영"을 남긴다.

## 7. 예외 상황

| 상황 | 처리 |
|---|---|
| 감액으로 새 계약 금액이 이미 청구한 금액보다 적다 | 막는다 (`amount_below_billed`). "청구한 인보이스를 취소·재발행해 금액을 맞춘 뒤 반영하세요" 안내. 감액 인보이스(마이너스 청구)는 지원하지 않는다 → 8장 결정 2 |
| 옛 단계를 일부만 청구했다 (500,000 중 300,000) | 300,000만 이월한다. 새 단계에서 나머지를 청구할 수 있다 |
| 반영 후 옛 인보이스를 취소 | 이월액이 자동으로 줄고, 새 단계에서 그만큼 다시 청구할 수 있다 |
| 반영 후 옛 인보이스를 재발행 | 승계를 따라 현재 단계로 배분한다. 한도가 부족하면 막는다 |
| v1 → v2 → v3 | 계보가 이어지므로 v1 청구도 v3 단계에서 합산된다 |
| 두 사람(두 탭)이 동시에 반영·청구 | 프로젝트 `version` 잠금 + 단계 행 잠금. 늦게 온 쪽은 `version_conflict` |
| 반영 전 v2 삭제 | 지금처럼 삭제할 수 있다 |
| 반영 후 v2 삭제 | 프로젝트가 참조하므로 막는다. v1도 승계 행이 참조하므로 막는다 |
| 같은 요청 재전송 | Idempotency-Key로 같은 응답을 돌려준다 |
| 작업 단위 청구(`task_id` 배분) | 계약과 무관하므로 영향 없다 |
| AI 분석 | 버전마다 따로 한다. v2 화면에 "v1 분석 결과는 이전 버전 기준" 안내 |
| 되돌리기 | 1차 범위 밖. v2 단계에 새 청구가 없을 때만 되돌리기를 2차에 검토 |

## 8. 결정이 필요한 것

| # | 질문 | 권장 | 다른 선택지 |
|---|---|---|---|
| 1 | 청구 후 변경을 어떤 계약서로 허용할까 | **같은 계약의 새 버전만** (이력이 한 계보에 남음) | 아무 계약서나 허용: 유연하지만 이력 추적이 흐려진다 |
| 2 | 감액으로 이미 청구한 금액보다 적어지면 | **반영을 막고 취소·재발행으로 맞추도록 안내** | 감액 인보이스(마이너스 청구) 기능을 새로 만든다: 범위가 크다 |
| 3 | 옛 단계에 걸린 초안 인보이스 | **새 단계로 자동 이동** | 초안을 먼저 지우게 한다: 단순하지만 손이 간다 |
| 4 | 이미 따로 올린 수정본(별개 계약서)을 기존 계약의 새 버전으로 묶는 기능 | 2차로 미룸 | 1차에 포함 |

## 9. 테스트 계획

**DB·서비스**
- 계보 합산: v1 청구 500,000이 v2 선금에서 이월로 잡힌다. v3까지 이어도 합산된다.
- 과다 청구 트리거: v1 선금 발행 500,000 + v2 선금 1원 발행 → 거부한다.
- 새 불변식: 현재 버전이 아닌 단계로 배분하는 초안·발행을 거부한다. 기존 발행 배분은 유효하다.
- 승계 행 수정·삭제를 거부한다.

**API**
- 정상 반영(예시 2장): 금액·단계·이월·청구 가능액, 감사 기록
- `carry_missing` / `carry_not_needed` / `carry_exceeds_term` / `amount_below_billed` / `revision_not_newer` / `revision_other_contract` / 남의 프로젝트 404
- 초안 자동 이동, 반영 후 옛 인보이스 취소 → 이월 감소, 재발행 → 현재 단계로 배분
- Idempotency 재전송, `version_conflict`
- 계약 목록·상세의 `project_id`가 v2 업로드 후에도 유지된다

**브라우저**
- 선금 발행·입금 → 수정 계약서 업로드 → 이전 값 비교 → 반영 확인 → 프로젝트 이월 표시 → 중도금 청구 → 선금 재청구가 막히는지
